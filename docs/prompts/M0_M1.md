# Prompts Claude Code — jalons M0 et M1

Emplacement conseillé : `docs/prompts/M0_M1.md` · S'appuie sur `CLAUDE.md`, `docs/SPEC.md` (v0.2) et `docs/DATA_SOURCES.md`.

## Mode d'emploi

Deux façons de s'en servir :

- **Piloté (recommandé).** Tu colles une seule fois le *prompt initial* ci-dessous. L'agent suit le « Protocole de pilotage » de `CLAUDE.md` : il déroule les étapes dans l'ordre, s'arrête à chaque point de contrôle et tient `docs/PROGRESS.md`. Tu réponds « go », « suite », « revue » ou « stop ». Ouvre une session neuve quand tu veux — au minimum à chaque changement de jalon, et après M1-1 et M1-2 qui chargent beaucoup le contexte : le *prompt de reprise* suffit.
- **Manuel.** Tu colles toi-même chaque bloc dans une session neuve, après avoir rempli les champs `‹…›`.

Dans les deux cas : chaque étape commence par **un plan que tu valides** ; l'agent ne pousse jamais (`git push`) de lui-même ; après **M1-1**, lis `docs/DATA_NOTES.md` toi-même avant de continuer, tout le reste repose dessus.

**Ordre.** P0 → M0-1 → M0-2 → M1-1 → M1-2 → M1-3 → M1-4 → M1-5 → Revue.
M1-3 ne touche pas au réseau : c'est l'étape à avancer si tu attends encore une réponse de l'équipe DofusDB.

**Avant de commencer, côté Marc.**
1. Dépôt GitHub créé et cloné, les quatre documents en place : `CLAUDE.md` à la racine, `SPEC.md` et `DATA_SOURCES.md` dans `docs/`, ce fichier dans `docs/prompts/M0_M1.md`.
2. Décisions D1 à D4 de SPEC §13 prises (ou valeurs par défaut acceptées).
3. Message envoyé à l'équipe DofusDB (D5). L'exploration M1-1 ne fait qu'une soixantaine de requêtes ; le **premier snapshot complet (M1-2) attend leur retour**.
4. Une adresse de contact à mettre dans les en-têtes des scripts.

Objectif : confronter DATA_SOURCES.md à l'API réelle et écrire docs/DATA_NOTES.md. Aucun code de production dans cette session : un script jetable dans scripts/explore/ suffit.

Règles réseau pour cette session :
- 60 requêtes maximum au total, une à la fois, 500 ms entre deux, vers api.dofusdb.fr uniquement. Tiens le compte et affiche-le.
- En-têtes : User-Agent « ‹Roadbook›/0.1 (projet fan non commercial ; +‹URL du dépôt› ; contact ‹adresse›) » et Referer ‹URL du dépôt›.
- $limit entre 1 et 3 pour observer la forme des objets. Liste complète autorisée seulement pour les types d'objectifs de quête et les super-types d'objets ; pour tout le reste, filtre.
- Sauvegarde chaque réponse brute dans data/raw/_explore/ (gitignored) et relis le cache avant de redemander quoi que ce soit.
- Au premier 429, ou à la deuxième erreur 5xx : arrête-toi et préviens-moi.

Questions auxquelles DATA_NOTES.md doit répondre, chacune avec un extrait JSON raccourci à l'appui :
1. /version : format exact.
2. Pagination : que renvoie $limit=100 ? $limit=0 donne-t-il total sans données ?
3. Quêtes : liste complète des champs de /quests/1329. Étapes, objectifs et récompenses sont-ils embarqués ? Sinon, les routes quest-steps, quest-objectives, quest-step-rewards, quest-objective-types et quest-categories existent-elles, et comment filtrer par quête ?
4. Types d'objectifs : table complète typeId → libellé français. Pour chaque type, où se trouvent l'ID d'objet, la quantité, l'ID de monstre, l'ID de PNJ dans les paramètres ? Propose la correspondance vers le type Objective de SPEC §5.
5. Récompenses de quête : où sont les objets et leurs quantités ? Quels champs pour « répétable » et « de groupe » ?
6. Objets : identifiant du type « Dofus » et du super-type des objets de quête. Sur un objet de type Dofus, questsThatReward est-il renseigné ? Combien d'objets de ce type ?
7. Succès : champs réels (points, niveau, ordre, lié au compte ?), forme exacte de need, nombre total, forme de readableCriterion sur un objectif.
8. Monstres et donjons : comment reconnaître un boss, comment relier un monstre à son donjon ?
9. /criterion : forme JSON exacte sur deux vecteurs de DATA_SOURCES §5.
10. En-têtes de réponse : indications de limite de débit ou de cache ?

## M1-2 — Client de snapshot

````
Lis CLAUDE.md, docs/DATA_SOURCES.md §3 et §6, docs/DATA_NOTES.md en entier.

Objectif : implémenter npm run data:snapshot dans scripts/snapshot/, conforme à l'étiquette réseau de DATA_SOURCES §3.

Comportement attendu :
- Appelle /version. Si data/raw/<version>/snapshot.json existe et est complet, ne fait rien et le dit.
- Phase A, tables complètes : quêtes et tables liées, succès et tables liées, tables de référence, donjons. La liste exacte des routes et des champs vient de DATA_NOTES.
- Phase B, entités référencées seulement : objets, monstres, PNJ (noms), recettes des objets référencés (un seul niveau), par lots id[$in][] de 50. Les IDs référencés sont calculés à partir de la phase A selon la correspondance établie dans DATA_NOTES.
- $select systématique : uniquement les champs listés comme utiles dans DATA_NOTES.
- Une requête à la fois, 250 ms minimum entre deux, attente exponentielle sur 429 et 5xx, arrêt propre après 5 échecs consécutifs.
- Cache disque par requête : relancer après une interruption ne retélécharge rien de ce qui est déjà là.
- Options : --dry-run (nombre de requêtes prévues par ressource, sans télécharger les données), --only <ressources>, --max-requests <n> (défaut 2000 ; au-delà, le script refuse de démarrer).
- Écrit data/raw/<version>/snapshot.json : version, dates, nombre de requêtes, total par ressource.

Qualité :
- Le client HTTP poli (cadence, reprise, cache) est un module isolé, testé avec un fetch simulé et une horloge injectée : cadence respectée, reprise après 429, arrêt après 5 échecs, relance sur cache. Les tests ne touchent JAMAIS le réseau.
- Journal lisible : une ligne par page, progression, temps restant estimé.

Méthode : plan d'abord. Ensuite lance --dry-run et montre-moi le décompte AVANT tout téléchargement réel, puis attends mon feu vert. ‹Je n'ai pas encore le retour de l'équipe DofusDB : arrête-toi après le dry-run.›

Critères de sortie : tests verts ; snapshot complet sous le budget ; une seconde exécution ne fait qu'une requête (/version) ; résumé avec le poids de data/raw/<version>/.
````

## M1-3 — Parseur syntaxique des critères (sans réseau)

````
Lis CLAUDE.md (règle d'or 5), docs/SPEC.md §6.1 et §6.8, docs/DATA_SOURCES.md §4 et §5.

Objectif : le premier étage du parseur, dans src/core/criteria/ : parseCriterionSyntax(raw) → Result<CriterionAst, ParseError>. Pur, sans dépendance.

Spécification :
- AST : { k: 'and' | 'or', items } ou { k: 'atom', key, op, args: number[], raw }. Aplatis les and/or imbriqués de même nature ; un groupe d'un seul élément se réduit à cet élément.
- Grammaire et opérateurs : DATA_SOURCES §4. Clé = exactement deux lettres, casse significative. Opérateur E accepté (« POE11563 »). Arguments : un ou deux entiers séparés par une virgule.
- Précédence : & avant |. Expose aussi hasMixedPrecedence(raw), vrai quand & et | se côtoient au même niveau sans parenthèses.
- Erreurs : jamais d'exception. ParseError porte la position et ce qui était attendu.
- printCriterion(ast) → forme canonique.

Tests, écrits d'abord :
- tests/fixtures/criteria.real.json : tous les vecteurs de DATA_SOURCES §5 recopiés à l'identique, quête 1329 comprise (attendu : 28 atomes Qf au premier niveau et un groupe or de 3).
- Propriété : pour chaque vecteur x, parse(print(parse(x))) est structurellement égal à parse(x).
- Quête 1317 : trois niveaux d'imbrication correctement rendus.
- Cas d'erreur : parenthèse non fermée, opérateur manquant, clé d'une seule lettre, argument non numérique, chaîne vide.

Hors sujet pour cette session : la traduction en Requirement (toRequirement), c'est M2.

Critères de sortie : tests verts ; couverture du module ≥ 95 % ; aucune règle ESLint de src/core désactivée.
````
