## M2-1 — Étage sémantique du parseur

`toRequirement(ast) → Requirement` et `parseCriterion(raw)`, table unique `criteria-map.ts` (clés « moteur », « contexte », le reste `unknown`), simplification (aplatissement, doublons, `all` d'un seul élément). `PL>n` → `level.min = n + 1` ; `PL<n` → `context` ; `!` → `not` ; `Ps!1&Ps!2` reste deux `not(alignment)`.
Critères de sortie : chaque vecteur de DATA_SOURCES §5 produit le `Requirement` attendu (attendus écrits à la main dans le test) ; `toRequirement` ne peut pas échouer ; couverture du module ≥ 95 %.

## M2-2 — Graphe et progression effective

`buildGraph(dataset)` : nœuds = quêtes et succès ; arêtes obligatoires (chemin de `all` seulement) ou alternatives (traverse un `any`) ; aucun arc à travers un `not` ; index inverse « débloque ». `computeEffectiveDone` : fermeture transitive des arêtes obligatoires depuis les coches explicites ; succès déductible quand tous ses objectifs sont `questDone`/`achievementDone` satisfaits.
Critères de sortie : sur la fixture 1329, 28 arêtes obligatoires directes et 3 alternatives ; cocher 1329 déduit ses 28 prérequis et leurs propres prérequis, jamais 710/711/1316 ; cycles et IDs manquants ne font rien planter.

## M2-3 — Résolution, points de choix, ordonnancement

`resolvePlan(graph, goal, character)` : racines, expansion, `ChoicePoint` avec identifiant déterministe (nœud porteur + position dans le critère), branche retenue selon SPEC §6.7, statuts (`done` › `implied` › `available` › `blocked` avec raisons), tri de Kahn à départage stable (`orderHint`, `levelMin`, `categoryId`, `id`), `DataIssue`.
Critères de sortie : sur 1329 la branche suit l'alignement du personnage (Bonta → 710, Brâkmar → 711, neutre → 1316, non renseigné → défaut) ; l'ordre ne change pas quand on coche un nœud ; Dotruche donne un plan de 5 nœuds ordonné.

## M2-4 — Besoins et conditions

Simulation d'inventaire (SPEC §6.6) avec tranches de niveau des récompenses, `ItemNeed` (dont `isQuestItem`, `providedBy`), monstres (`singleFightMax`), donjons (via `dungeonIds`), conditions (niveau, métiers, alignement, classe, contexte).
Critères de sortie : cas `FAKE` montré puis donné, donné puis montré, récompense intermédiaire, quantité possédée, récompense dépendant du niveau ; besoins calculés sur les trois fixtures réelles sans erreur.

## M2-5 — Intégration au dataset et test de fumée

`data:build` compile `start` en `Requirement` (chaîne brute conservée, AST retiré), `listGoalCatalog`, test de fumée : résoudre chaque quête et chaque succès du dataset comme objectif sans exception, mesurer `buildGraph` et `resolvePlan`. `data:report` : écart entre nos prérequis calculés et le champ `need` de DofusDB, expliqué dans DATA_NOTES.
Critères de sortie : aucun échec sur l'ensemble du dataset ; `buildGraph` < 300 ms et `resolvePlan` < 50 ms sur la machine de dev ; poids du dataset toujours sous la cible.
